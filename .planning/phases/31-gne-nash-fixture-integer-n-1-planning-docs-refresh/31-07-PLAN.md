<objective>
Fix Phase-30 code review WR-03 (`.planning/phases/30-socp-in-the-loop-benders-on-a-multi-bus-feeder/30-REVIEW.md`), carried over as part of BILEV-07's "Phase-30 open integer-path review warnings are FIXED here" decision (`31-CONTEXT.md`). Plan 31-01 found that WR-03's directed fix -- **Option B**, widening `solve_stackelberg!`'s convergence certificate by `_accepted_lb_slack` -- breaks the project's own flagship pinned Benders goldens at the standard `tol=1e-6` (see `31-01-SUMMARY.md`'s Deviations section in full) and recommended **Option A** instead: clamp an accepted-but-slack explicit bound DOWN to the certified derivation minimum AT BUILD TIME, so the runtime certificate never needs widening in the first place.

This plan implements Option A in BOTH `build_master` (`src/planning/master.jl`) and `build_master_integer` (`src/planning/master_integer.jl`): when an explicit `α_op_lb`/`α_x_lb` is ACCEPTED (does not exceed `d.optimum + slack`, the existing rejection ceiling -- UNCHANGED by this plan) but lies strictly ABOVE the certified `:auto`-equivalent minimum `d.bound = d.optimum - alpha_lb_margin(d.optimum, d.gap)`, the value actually installed on the epigraph variable is `min(requested, d.bound)` -- the SAME value `:auto` would install -- rather than the raw requested value. A bound already at or below `d.bound` (every pre-existing call site: this project's own `-5.0`/`-50.0` toy-fixture literals) passes through completely unchanged. The clamp amount (0.0 when none was needed) is recorded on a new `lb_clamped` field on both master structs, so a caller's requested value is never silently discarded, only tightened to a sound one.

Because the installed bound can now never sit above `d.bound` for ANY accepted explicit bound, the build-time acceptance slack `lb_slack` (read via the pre-existing `_accepted_lb_slack` dispatcher, `benders.jl`) becomes `(; op=0.0, x=0.0)` in every case -- the residual LB inflation WR-03 is about is provably zero after this fix. `solve_stackelberg!`'s convergence certificate and `_assert_epigraph_floor`'s runtime guard (both in `benders.jl`) are therefore left COMPLETELY UNTOUCHED by this plan -- Option A resolves WR-03 entirely at the two build-time call sites, never by loosening a runtime/convergence check (Option B stays rejected, exactly as 31-01 concluded).

Purpose: close WR-03 for BOTH master types without moving a single pre-existing pinned golden, and without ever touching `solve_stackelberg!`'s convergence formula.
Output: `src/planning/master.jl` and `src/planning/master_integer.jl` with the build-time clamp and a new `lb_clamped` field; three updated test files proving (a) the clamp fires exactly inside the slack band, (b) every pre-existing call site is byte-identical, and (c) the installed bound can never exceed the true relaxed minimum.
