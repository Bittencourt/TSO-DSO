# Quick Task 260726-vn2: Bounded retry for the flaky IEEE-13 `solve_admm` test items

## Why

Two test items intermittently ERROR with `assert_solved!`'s "Solve failed — refusing to trust
results" (`src/core/status.jl:57`) — the documented Clarabel `NUMERICAL_ERROR`-class flake
(Phase 16-04 measured ~55% baseline single-call rate on IEEE-13 `solve_admm` with
`reactive_consensus=false`; version-independent, observed on both Julia 1.10 and 1.12 CI runs,
same two items each time):

- `test/test_acceptance.jl:23` — `"acceptance: IEEE-13 congestion — exact relaxation + DADP +
  ADMM≈centralized (SC3)"`
- `test/test_admm.jl:67` — `"admm: cross-validation ieee13 welfare + DADP (crossval, ieee13)"`

Both items call `solve_admm` on the SAME congested IEEE-13 ground fixture at `ρ=100`
(`src/admm/solve_admm.jl`) — the one call path this flake is pinned to. The fix retries ONLY
that call, never the assertions around it.

## Scope

Add a small **test-only** bounded-retry helper (shared `@testmodule`, not `src/`) that retries a
zero-argument `solve_admm(...)` closure up to N=3 total attempts, catching ONLY
`assert_solved!`'s exact error signature (an `ErrorException` whose message starts with
`"Solve failed — refusing to trust results"`), `@warn`-logging every failed attempt with the
attempt number, and rethrowing on exhaustion. Every existing assertion in both test items stays
byte-identical — only the `solve_admm(...)` call itself is wrapped.

`solve_admm` itself (`src/admm/solve_admm.jl`) is NOT modified — it must not auto-retry; this is
test-infrastructure only, mirroring the *pattern* of `src/planning/retry.jl`'s
`solve_with_retry!` (escalating conditioning ladder around a different choke point) but living in
`test/` and doing a plain re-call, not a solver-attribute escalation, since these two items solve
via `solve_admm`'s own internal `assert_solved!` calls, not a caller-owned `Model`.

## Tasks

### Task 1 — create the shared retry fixture module

- **files:** `test/fixtures_retry.jl` (new)
- **action:** Add a new `@testmodule AdmmRetryFixtures begin ... end` block (same idiom as
  `test/fixtures_phase4.jl`'s `Phase4Fixtures` — TestItemRunner auto-discovers `@testmodule`s
  project-wide; no `include` needed) defining one function:

  `retry_flaky_admm_solve(f::Function; max_attempts::Int = 3, label::AbstractString = "solve_admm")`

  Behavior: guard `max_attempts >= 1` (else `throw(ArgumentError(...))`). Loop `attempt in
  1:max_attempts`: `try; return f(); catch e; ...`. Inside the catch, first test
  `e isa ErrorException && startswith(e.msg, "Solve failed — refusing to trust results")` — the
  EXACT message prefix `assert_solved!` emits (`src/core/status.jl:57-63`; match on prefix only,
  not the full multi-line diagnostic, since `termination_status`/etc. vary). If that test is
  false, `rethrow()` immediately (attempt 1 and every attempt) — a genuinely different failure
  (a different `ErrorException`, an `ArgumentError` boundary guard, `solve_admm`'s own
  `"solve_admm FAILED to converge"` maxiter message, or `assert_no_slack`'s "Hidden constraint
  slack detected" message) must NEVER be swallowed. If it IS the known flake signature,
  `@warn` with the label, the attempt number out of `max_attempts`, and the caught message, then
  `attempt == max_attempts ? rethrow() : continue` (i.e. rethrow only after the last attempt).
  Do NOT vary any input between attempts — each retry is a fresh, identical `solve_admm(...)`
  call from the caller's closure (the flake is Clarabel's iterate path varying run-to-run on
  IDENTICAL seeded inputs, not a deterministic input problem — RESEARCH note in this task's
  planning context).
- **verify:** `julia --project=test -e 'include("test/fixtures_retry.jl")'` parses with no error
  (the `@testmodule` macro is a no-op outside TestItemRunner discovery, so a bare `include` only
  checks syntax — this is a syntax smoke check, not a functional test).
- **done:** `test/fixtures_retry.jl` exists, defines `AdmmRetryFixtures.retry_flaky_admm_solve`
  exactly as specified above, and no other file is touched by this task.

## Constraints

- Assertions/tolerances/gates stay byte-identical (decision #5) — only the solve call is
  wrapped, confirmed by `git diff` showing no changed `@test` lines.
- Catch narrowly on error type + message prefix (decision #2) — a genuinely new failure mode
  (different message, different type) must still propagate and fail the test.
- `@warn` every retry attempt with the attempt number (decision #3).
- Rethrow on exhaustion — test must still fail on a persistent failure (decision #4).
- Shared helper in a test-only file, not duplicated across the two test files, not added to
  `src/` (decision #6) — `solve_admm` must not auto-retry.
- Retry is a plain re-call from identical seeded inputs; no input perturbation between attempts
  (decision #7) — the flake is Clarabel's non-deterministic iterate path, not a deterministic
  input issue.
