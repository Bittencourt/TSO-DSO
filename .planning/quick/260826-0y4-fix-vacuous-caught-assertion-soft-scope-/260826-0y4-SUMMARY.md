# Quick Task 260826-0y4: Fix the vacuous `caught` assertion (soft-scope bug) + record detection method Summary

**Let-wrapped the INT-03 certification item's `caught`/`caught_bt`/`result` state (the second application of the D-06 let-idiom, commit d8e8999), turning `@test caught === nothing` from a permanently-vacuous assertion into a genuine gate -- proven by a negative control where the pre-fix shape PASSES under a forced throw and the post-fix shape correctly FAILS and surfaces the exception via `@error`.**

## Performance

## Accomplishments

- Replaced the misdiagnosed "Scoping note" comment (previously blaming a
  "TestItemRunner-only failure" / "harness artifact") with a corrected comment that
  keeps the still-true guidance (`result = try ... end` takes the try EXPRESSION's own
  value, unaffected by scope class), states the real cause (ordinary Julia
  soft-scope-ambiguity for module-top-level `@testitem` bodies), states the second
  and more serious defect this task fixes (the vacuous `caught = e` dead local), states
  the fix (the `let`-wrap idiom), and points to `test/runtests.jl`'s header for the
  durable detection method.
- Moved `caught`, `caught_bt` (new — `catch_backtrace()`), `result`, and the
  `mktempdir()`-derived checkpoint dir into a `let` block (a hard scope), destructured
  at the `@testitem` top level immediately after — the `solve_stackelberg!` call's
  arguments are byte-identical to before.
- Inserted `if caught !== nothing; @error "solve_stackelberg! threw during the
  certified (known_optimum-matched) run" exception = (caught, caught_bt); end`
  immediately before the existing `@test caught === nothing`, so a future genuine
  throw prints the exception and backtrace instead of a bare `Bool` failure.
- **Negative control (the load-bearing proof):** wrote throwaway BEFORE/AFTER
  reproduction scripts. Discovered mid-task that the plan's literal `module ... end`
  wrapping form does NOT reproduce Julia's "soft scope is ambiguous" warning at all
  (measured directly — see Decisions) because TestItemRunner evaluates `@testitem`
  bodies via `Core.eval(fresh_module, body_expr)`, not a `module` syntax block.
  Rewrote both scripts to use `Core.eval(Module(), quote ... end)` for a faithful
  reproduction. Result: the BEFORE (buggy) shape's `@test caught === nothing` PASSED
  (`exit=0`) despite a forced `error(...)` throw, with the soft-scope warning firing
  (count=1); the AFTER (fixed) shape's `@test caught === nothing` correctly FAILED
  (`exit=1`) under the identical forced throw, printed the exception via `@error`
  (`SYNTHETIC THROW` count=2 in the log — once in the `@error` block, once in the
  `@test` failure report), and printed zero soft-scope warnings.
- **Real INT-03 item, twice consecutively:** ran the certified item via
  `JULIA_LOAD_PATH="$PWD/test:$PWD:@stdlib" julia -e 'using TestItemRunner, TSODSO;
  TestItemRunner.run_tests(...)'` filtered to the INT-03 item. Both runs: `Pass 14 /
  Total 14`, `exit=0`, `grep -c "soft scope is ambiguous"` returned `0` on both logs —
  the item genuinely passes now that the gate is real, and `solve_stackelberg!` does
  NOT throw on this fixture (no blocker finding to report).
- Appended a detection-method paragraph to `test/runtests.jl`'s header documenting the
  bug class, both known instances (D-06, this task), the authoritative detector (grep
  a full-suite run log for `"soft scope is ambiguous"`, must be `0`), the fix idiom,
  and the measured `Core.eval`-vs-`module`-syntax nuance above.
- Added a `LIMITATIONS` paragraph to `softscope_scan.py`'s docstring recording its
  measured false-positive rate (15 candidates, mostly noise on this repo's suite) and
  that it MISSED the one real instance that existed at scan time, because its
  opener-tracking regex desynchronises on `if`/`let`/`function`/`begin` blocks
  interleaved with the tracked `for`/`while`/`try` openers.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug in verification approach] Negative-control scripts didn't reproduce the warning as literally specified**
- **Found during:** Task 2, step 1 (BEFORE negative control)
- **Issue:** The plan's literal `module BeforeFix ... end` / `module AfterFix ... end`
  wrapping form, run via `julia --project=. script.jl`, printed no "soft scope is
  ambiguous" warning at all — verified directly (see Decisions) that Julia only emits
  this specific warning when code is evaluated via `Core.eval(mod, block_expr)`
  (TestItemRunner's actual `@testitem`-body evaluation mechanism), not for a literal
  `module ... end` syntax block or a plain script/`include`/`-e` top-level run.

  body into it via `Core.eval`, faithfully mirroring TestItemRunner's real mechanism.

  documented in `test/runtests.jl`'s committed header paragraph so it's not lost.
- **Verification:** BEFORE script: `exit=0` (vacuous pass) with `soft scope is
  ambiguous` count `1`; AFTER script: `exit=1` (genuine fail) with count `0` and
  `SYNTHETIC THROW` count `2`.
- **Commit:** not applicable (verification-only artifacts); the documentation of the
  finding is part of commit `79c1107`.
