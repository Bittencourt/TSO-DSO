# Quick Task 260825-w5a: Retire the no-op `AdmmRetryFixtures.retry_flaky_admm_solve` helper

## Why

`AdmmRetryFixtures.retry_flaky_admm_solve` (`test/fixtures_retry.jl`, added by quick task
260726-vn2) re-calls its wrapped closure with **no input perturbation and no solver-attribute
change** between attempts. Two things established this session prove it cannot work and never
worked:

1. **It cannot work by construction.** The failure it targets (Clarabel `NUMERICAL_ERROR` at
   ADMM iteration 28 on the congested IEEE-13 `ρ=100` ground fixture) is **deterministic per
   (source tree × Julia version)** — `.planning/debug/resolved/ieee13-admm-numerical-error.md`
   measured 5/5 identical failures on a failing toolchain, not the ~55% the helper's docstring
   still describes. Re-running an identical deterministic computation cannot change the outcome.
2. **It never fired in anger.** `grep` for its `@warn "retry_flaky_admm_solve: ..."` across all
   3 Julia jobs of the failing CI run (32791955335) returns zero hits.

The REAL fix landed this session as commits `f9d6ed7` (mid-loop `solve_dso!` routed through
`solve_with_retry!`) and `d099821` (RESET-01: the ladder is reset to the as-built baseline before
every `check_exact = true`/published solve). This is a **caller-independent, production-level**
fix inside `src/admm/DsoOpt.jl`'s `solve_dso!` — every `solve_admm` call, from any test or
scenario, now re-solves the mid-loop DSO-OPT through the 4-rung Clarabel conditioning ladder
whenever it hits a status in `RETRYABLE_STATUSES` (`MOI.NUMERICAL_ERROR` included). CI run
32910604313 on `9ed6185` is green on all 5 jobs. `test/fixtures_retry.jl`'s test-level wrapper is
now dead weight, and worse, it is a latent hazard: it swallows the first N-1 occurrences of
**any** `ErrorException` whose message starts with `"Solve failed — refusing to trust results"` —
`assert_solved!`'s signature for **every** non-OPTIMAL status, including genuine `INFEASIBLE`/
`DUAL_INFEASIBLE` modelling failures, not just numerical ones.

## Decision

**Option (A): DELETE `test/fixtures_retry.jl` and unwrap every call site to a plain `solve_admm`
call**, for all three sites — no differentiated treatment. Evidence:

- All three call sites (`test/test_admm.jl`, `test/test_ieee123_admm.jl`, and — discovered during
  this planning pass, see below — `test/test_acceptance.jl`) drive the **same** congested IEEE-13
  `ieee13_modified()` ground fixture from `Phase4Fixtures.build_ieee13_ground_aggregators`, all
  starting `ρ = 100.0` (`ρ_ieee13`/literal `100.0`). `solve_admm`'s adaptive-ρ kwargs
  (`τ = 2.0`, `μ = 10.0`, `ρ_min = 1e-2`, `ρ_max = 1e4`, `ε_abs = 1e-4`, `ε_rel = 1e-3`,
  `src/admm/solve_admm.jl:57-58`) are ON by default at every one of these call sites (none override
  them), so all three can climb `ρ₀ = 100 → ρ = 200` exactly like the debug session's repro and
  land on the same iteration-28 knife-edge.
- The fix that rescues that knife-edge lives in `solve_dso!`'s **mid-loop branch**
  (`src/admm/DsoOpt.jl`), which every `solve_admm` call passes through regardless of which test
  file or fixture called it. There is nothing IEEE-13-fixture-specific or call-site-specific left
  for a test-level wrapper to add.
- The genuine IEEE-123 `@testitem`s in `test/test_ieee123_admm.jl` (the "end-to-end converge +
  DADP cross-validation" and "voltage-binding margin" items) **never used `AdmmRetryFixtures`
  at all** — confirmed by `grep -rn "AdmmRetryFixtures" test/`, only 3 real call sites exist,
  all three on the IEEE-13 ground fixture, none on IEEE-123. So the caveat "IEEE-123 flakiness was
  never characterized this session, do not assume IEEE-13 findings transfer" is moot here: there
  is nothing to unwrap on IEEE-123, because IEEE-123 was never wrapped.
- Per-file reasoning is therefore identical for all three sites, not because IEEE-13 findings were
  blindly extrapolated, but because all three sites reduce to the exact same fixture/ρ/code path
  the debug session measured directly.

**Scope correction found during planning — read before touching files.** The quick task's own
`<files_to_read>`/"Files in scope" list names only `test/fixtures_retry.jl`, `test/test_admm.jl`,
and `test/test_ieee123_admm.jl`. A repo-wide grep (`grep -rn "AdmmRetryFixtures" test/`) found a
**third, unlisted call site**: `test/test_acceptance.jl:24` (setup list) and `:64`
(`AdmmRetryFixtures.retry_flaky_admm_solve(; label = "acceptance ieee13") do ... end`), driving the
same `ieee13_modified()` fixture at `ρ = 100.0`. Deleting the shared `@testmodule
AdmmRetryFixtures` without also unwrapping this call site would leave `test_acceptance.jl` with an
undefined `setup` reference and break the suite. `test/test_acceptance.jl` is therefore added to
this plan's file scope; it gets **exactly the same treatment** as the other two sites, for exactly
the same reason (same fixture, same ρ, same caller-independent production fix).
