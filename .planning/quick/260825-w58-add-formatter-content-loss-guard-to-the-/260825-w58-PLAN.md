# Quick Task 260825-w58: Formatter content-loss guard in CI

## Why

JuliaFormatter 2.10.2 with `format_docstrings = true` (a deliberately kept, LOCKED
`.JuliaFormatter.toml` setting — do not propose changing it) SILENTLY DELETES docstring text
when an inline code span wraps across a line break and the continuation line begins with `|`
(CommonMark reads that continuation as a markdown table row and drops it during reflow). This
cost 148 characters of `src/models/restriction_exactness.jl`'s module docstring during quick
task 260824-vxn; the formatter is idempotent after the damage, so CI would have reported GREEN
with the text silently missing. It was only caught because an executor diffed content instead of
trusting the format gate. `.planning/STATE.md`'s "Standing hazard" note names this task (B2:
"add a formatter content-loss guard to the CI format job") as the closure.

A working, smoke-tested detector already exists at
`.planning/quick/260825-w58-add-formatter-content-loss-guard-to-the-/check_content_loss.py`:
`python3 check_content_loss.py <git-ref>` walks every tracked `.jl` file under `src/ext/test/docs`,
compares the working-tree content against `git show <ref>:<path>` with ALL whitespace and commas
stripped, and exits 1 with a per-file character-delta list if anything else differs. It currently
lives only in this task directory and a session scratchpad — it must be committed somewhere real
to be usable by CI, and wired into the `format:` job.

**REVISION (this version fixes a no-op bug a coordinator review caught in the prior draft).** The
guard must fire at the ONE moment content loss is actually observable: while `format([...])` is
rewriting files in place during THIS CI run. Traced through both branches of the existing
`format:` job:

- **CASE 1 — repo already format-clean.** `format([...])` writes nothing, returns `true`. A guard
  compared against `HEAD` here is comparing an unchanged tree to itself — it can only ever pass
  trivially. This is fine; there is nothing to catch in this case.
- **CASE 2 — repo is NOT format-clean (the real hazard case).** `format([...])` REWRITES the files
  on disk — this is the exact moment that can silently delete docstring text — THEN returns
  `false`, and the step's own `exit(1)` fails the step. **If the guard step is only scheduled to
  run "on success" (the prior draft's implicit default sequencing), GitHub Actions SKIPS it
  entirely, precisely because step 1 failed.** The one case where the guard has something to catch
  is the one case a plain "runs after success" step never executes in. This is exactly the
  real-world sequence that shipped the historical incident: a `|`-wrapped docstring lands
  unformatted, CI's format check fails, a developer runs the formatter locally to "fix" the
  failure, the formatter eats 148 characters as a side effect, they commit the now-"clean"-but-
  damaged file, and CI goes green forever after with the text silently gone. The guard's real job
  is to warn the developer AT THE MOMENT OF THE CI FAILURE — "do not just re-run the formatter
  and commit, it will delete text from src/models/X.jl" — before that local "fix" ships.

  **Fix:** the guard step is given `if: always()`, so it runs regardless of whether the prior
  format-check step passed or failed (see Task 2 for why this cannot mask a red job as green).

**Honesty about what this guard can and cannot do (decision point 2, per coordinator review):**
This guard can ONLY catch content loss introduced by a formatting pass that runs DURING this CI
job — i.e. `HEAD` (the committed, checked-out state) must still hold the good content at the
start of the run, and `format([...])` must be the thing that damages it. It CANNOT catch damage
that is already committed: if a docstring was already mangled by a prior local `format()` run and
committed in an already-format-clean state, `HEAD` itself holds the loss, `format([...])` makes no
further change (idempotent), and the guard's working-tree-vs-`HEAD` diff is empty by construction
— there is nothing to observe. This is precisely how the original 148-character loss entered
history in the first place (quick task 260824-vxn's local reformat), and this guard, had it
existed then, would NOT have caught that specific commit after the fact. It closes the door on the
mechanism going forward (any future CI-run formatting pass that damages content), not on damage
already sitting in history. A complementary approach for the already-committed case is proposed as
a follow-up below — deliberately kept out of this plan's scope.

**Validated this session** (see Task 3, extended for both CASE 1 and CASE 2): running the pinned
2.10.2 formatter over the ORIGINAL (pre-`a8f7659`) wrapped-`|` docstring in a throwaway fixture
repo reproduces the exact historical -148 character loss. Two things were proven directly, by
executing the real CI logic against the fixture:
1. The format-check step's own `if !format(...) ... exit(1) end` logic really does exit 1 against
   the unformatted trigger-pattern file (CASE 2's first half).
2. Even after that exit(1), running the guard afterward (simulating `if: always()`) against the
   same fixture's `HEAD` still catches the loss: `CONTENT LOSS in 1 file(s): chars -148
   src/restriction_exactness.jl`, guard exit code 1 (CASE 2's second half — the part the prior
   draft silently skipped).
The current real repo tree passes clean today (exit 0, 183 files checked, CASE 1).

**Explicitly NOT in scope:** `.JuliaFormatter.toml` (locked `format_docstrings = true` — do not
edit), any reformatting of real source files, the pinned JuliaFormatter version string in
`.github/workflows/CI.yml` (`version = "2.10"` — leave the `Pkg.add(PackageSpec(...))` line and
its guard comment exactly as-is), the `test:`/`docs:` CI jobs, and the complementary
already-committed-damage lint proposed in the Follow-up section below.

### Task 2 — wire the guard into the CI `format:` job, so it runs even when formatting fails

- **files:** `.github/workflows/CI.yml`
- **action:**
  1. Immediately after the existing `Install JuliaFormatter and check formatting` step (do not
     modify that step's content, its `shell:` override, its `Pkg.add` pin, or its `exit(1)` gate),
     add a new step in the `format:` job named `Check for formatter content loss`, with:
     - `if: always()` — REQUIRED. Without this, GitHub Actions' default sequencing skips a step
       after a prior step fails, which is precisely CASE 2 (see Why) — the one case the guard
       exists to catch. `always()` makes the step run whether the prior step passed OR failed
       (`exit(1)`), so the guard can inspect whatever `format([...])` just wrote to disk in either
       branch.
     - `shell: bash` (explicit — the prior step overrides to `shell: julia --color=yes {0}`; this
       step must NOT inherit that override, since `check_content_loss.py` is a plain Python
       script).
     - `run:` a single line: `python3 .github/scripts/check_content_loss.py HEAD`.
  2. Above that `run:` line, add a comment recording BOTH decisions from this task's design review:
     (a) why `if: always()` is required — CASE 2 (the format step rewriting-then-failing on a
     dirty repo) is exactly the moment content loss is observable, and a plain "runs on success"
     step would skip it every time; (b) why this cannot turn a red job green — GitHub Actions
     computes job conclusion from ALL steps' conclusions (any step failing, `always()`-gated or
     not, fails the job), so if the prior step exits 1 the job is ALREADY failing regardless of
     what the guard step reports; `always()` only controls whether the guard step RUNS, not
     whether its result can override an earlier failure. Reference the historical incident (148
     chars lost from `src/models/restriction_exactness.jl`, commit `a8f7659`) as the concrete
     justification, and reference `HEAD` as the correct comparison ref: `format([...])` already
     runs with the default `overwrite=true`, so by the time this step runs (in either the pass or
     fail branch), `src/ext/test/docs` already holds whatever the pinned formatter just wrote to
     disk, while `git show HEAD:<path>` still holds the untouched pre-format checkout (nothing
     else has written to those paths since `actions/checkout@v4`).
  3. Do NOT restructure the existing format-check step to remove its `exit(1)` (e.g. splitting
     "format" and "assert clean" into two steps) — `if: always()` on the guard step alone is
     sufficient and keeps the change minimal; see the Why section's validated proof that this
     shape actually fires in CASE 2.
  4. Do not add, remove, or reorder any other job or step. Do not touch the `test:` or `docs:`
     jobs.

## Follow-up (proposed, explicitly OUT OF SCOPE for this plan)

This guard only catches content loss introduced by a formatting pass that runs during a CI job —
it structurally cannot catch loss that is already baked into a committed, already-format-clean
`HEAD` (see Why section). A complementary, clearly-separate follow-up worth considering as its own
future quick task: a static lint (grep/regex, no formatter invocation needed) that scans `.jl`
docstrings for the trigger PATTERN itself — an inline code span (odd number of backticks opened,
not yet closed) that wraps across a line break where the continuation line's first non-whitespace
character is `|` — and flags it regardless of whether the formatter has run yet. That would catch
the hazard at authoring time, and also retroactively over existing history (run once against
`HEAD` today, and optionally as a pre-commit/CI hook going forward) — covering exactly the gap
this session's guard cannot reach. Not included here: it is a different detection mechanism (static
pattern match vs. before/after diff), deserves its own validation against false positives (e.g.
legitimate markdown tables inside a docstring), and would expand this plan past its 3-task budget.
