# Quick Task 260825-w58: Formatter content-loss guard in CI Summary

**CI's `format:` job now runs a second, `if: always()`-gated step that diffs the post-format working tree against `HEAD` (whitespace/comma-insensitive) and fails with the offending file + char-delta if JuliaFormatter silently deleted docstring content during that run — proven in this session to actually fire against the real historical -148-char defect.**

## Accomplishments

- Committed the previously scratchpad-only `check_content_loss.py` detector to a real,
  CI-reachable path: `.github/scripts/check_content_loss.py`.
- Wired it into `.github/workflows/CI.yml`'s `format:` job as a new step,
  `Check for formatter content loss`, with `if: always()` so it runs whether the prior
  format-check step passed or failed — the fix for a no-op bug a coordinator review caught

## Decisions Made

- Kept the guard step minimal and additive (no restructuring of the existing format-check
  step into "format" + "assert" halves) — `if: always()` alone was sufficient and is what
  this session validated against the real fixture.
- Used `HEAD` as the comparison ref rather than a separate pre-format snapshot step, since
  `actions/checkout@v4` guarantees `HEAD` and the working tree start identical and nothing
  else touches `src/ext/test/docs` before the format step runs.

## What This Guard Cannot Do (documented per plan's honesty requirement)

This guard only catches content loss introduced by a formatting pass that runs DURING a CI
job — `HEAD` must still hold good content at job start, and `format([...])` must be what
damages it. It structurally cannot catch damage already baked into a committed,
already-format-clean `HEAD` — which is exactly how the original 148-character loss entered
history (a local reformat in quick task 260824-vxn, committed already-clean). A complementary
static-lint approach for that already-committed case is proposed in the plan's `## Follow-up`
section and is explicitly out of scope for this task.
