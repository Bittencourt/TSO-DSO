<objective>
Implement PM-07 (locked decision, `26-CONTEXT.md`'s post-merge amendment): "Add the thesis 3.37
receiving-end limit to `ACPowerFlow` too, so AC-vs-SOCP comparisons share a feasible set." This is a
LATENT issue flagged (not currently failing) by `26-POSTMERGE-TRIAGE.md`: Plan 26-05 (FIX-03) added
the receiving-end apparent-power cone `:smax_rev` (thesis 3.37) to `ConvexBranchFlow`/`MeshedFlow`/
`RestrictedBranchFlow`, but `ACPowerFlow` (`src/powerflow/ACPowerFlow.jl`, the Ipopt AC-OPF oracle)
still enforces ONLY the sending-end limit `:smax` (thesis 3.36). On IEEE-13, `:smax_rev` binds under
PV back-feed on the limited head branch — so any AC-oracle comparison against a limited branch under
back-feed currently compares DIFFERENT feasible sets (the AC oracle is strictly LESS restricted
there than the SOCP formulations it is meant to validate against).

Purpose: give the AC oracle the SAME apparent-power feasible set the SOCP formulations enforce, so
AC-vs-SOCP comparisons (exactness certification, DADP cross-checks) are apples-to-apples on every
limited branch, not just the sending end.
Output: `ACPowerFlow.contribute!` gains a `:smax_rev` scalar-quadratic inequality, registered under
the identical filter `:smax` uses; a new PV back-feed regression in `test/test_ac_powerflow.jl`
mirroring `ConvexBranchFlow`'s own FIX-03 test.
</objective>
