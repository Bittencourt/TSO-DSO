The Case A population — 784 houses over the IEEE-13 feeder

Every other page of this manual populates its feeder with one residential Aggregator per load bus. The thesis's Case A study instead works at a true 784-house population scale — and this page documents, for a reader who never opens the source: how that population is constructed, how it is calibrated, what it actually contains (measured live at docs-build time), what the centralized and decomposed solve engines agree on (measured, and honestly qualified), how solve cost scales with population size and with thread count (measured), and which thesis parameters were NOT available when the population was built — with the exact rule that replaced each one.

One structural fact shapes the whole design: the decomposed (ADMM) solver requires EXACTLY one aggregator per load node — it throws on any other count — and the centralized price extraction needs one unique bus row per load node. The 784 houses are therefore rolled up, at construction time, into exactly 10 bus-level Aggregators (the houses' device lists concatenated, their inelastic demands summed). The house-level granularity is not lost: it lives in the construction itself (every house draws its own seeded profile and its own device parameters), in the pure TSODSO.case_a_household_map accessor, and in the composition statistics below.

Construction rule

TSODSO.build_population(:case_a_784, ...) over the modified IEEE-13 feeder builds the population. Three rules fully determine it; each one is test-enforced in test/test_population_case_a.jl.

Per-bus house counts. The houses are distributed over the 10 load buses proportionally to the default population's per-bus counts — which on this feeder is exactly ONE house per bus (a uniform signal, so "proportional" degenerates to equal shares). Every bus receives the base share total ÷ length(buses); the residue total % length(buses) is handed out +1 per bus to the FIRST buses in ascending bus-id order. That tiebreak is a documented specialization: the rule's original "largest buses first" language carries no size signal on a uniform base, so it resolves to bus id. The live tally below prints the resulting table.

Per-house seeding. Every house's profile draw is seeded by Int(hash((s_pop, :house, bus, house_index)) % typemax(UInt32)) with s_pop = sub_seed(master_seed, :population) — the materializer's standard hash idiom extended with a richer tuple. The derivation is deliberately per-HOUSE: the older seed + bus idiom gives every house on a bus the IDENTICAL draw, which would silently collapse this population to ten distinct houses repeated over and over. The tests assert that all 784 seeds are distinct, that rebuilding reproduces the population exactly, and that all 784 full profile draws are distinct.

The PV-ownership group. Every household-map row carries a pv_group field from a generic rule (:pv when house_index ≤ ceil(pv_fraction × houses_on_bus), else :non_pv). At the named constant _CASE_A_PV_FRACTION = 1.0 every house is :pv — which is the honest reading of the locked calibration decision below, because the default population is all-PV (every house carries a PVBattery). The field is deliberately generic: a later phase can lower the constant without redesigning anything.

The live slice below builds the population and tallies the household map. It is build-only work — seeded random draws and struct construction:

Calibration provenance

Per-house magnitude scale. Each house's device magnitudes use the IEEE-13 residential scales DIVIDED by its bus's house count. The rationale is load-bearing: dividing by houses-per-bus preserves each bus's aggregate load and PV at the validated default level, keeping both solve engines in the known-good congestion/voltage regime that the one-house-per-bus proxy was calibrated in. Raw per-house scales would instead put roughly 78× the calibrated load through the 6.86 MVA head branch — near-certainly infeasible, which would render every agreement and scaling measurement meaningless. The printout below shows the constants doing the dividing.

Fractions kept from the default population. The PV/non-PV split and the elastic/inelastic proportions are the default population's OWN — continuity with the validated rescaled proxy is the whole calibration principle, and nothing about this population is re-tuned.

Thesis reference totals, stated as context only. The thesis's Case A specification targets PV = 5 MWp, elastic = 6.5 MW and inelastic = 1.5 MW. Those totals are recorded here as PROVENANCE CONTEXT, not as a target: this construction deliberately does NOT chase absolute thesis megawatts. What it preserves is the validated per-bus solve regime at the true house count. Matching the thesis magnitudes is an ablation-study concern for a later phase, and would be a measured, documented change of its own.

Agreement — measured at the full population

The protocol is gate-then-golden: run BOTH solve engines on the SAME built population FIRST, record the observed welfare and price deltas, and only then pin any test band derived from that measurement — never pre-loosened, never hand-picked. The band's home is the :slow-tagged test item in test/test_population_case_a_agreement.jl, deliberately excluded from the default CI lane so the fast suite stays fast.

This section reads committed data; nothing is solved at build time

Regenerate the measurement row with:

julia --project=. scripts/case_a_agreement.jl --agr-rung gap_1e-10

The script upserts its row — keyed on Julia version, seed, horizon AND solver rung (agr_tol) — into results/case_a_population/agreement.csv; re-runs replace their own row and never drop others.

The measured row, read here at build time:

# Read a committed measurement CSV with `Base` only — the docs environment pins a
# deliberately minimal dependency set (no CSV/DataFrames; the same convention as
# the Scaling to IEEE-8500 page's reader). These CSVs contain no quoted commas, so
# a plain per-line split is exact. An EMPTY cell is a deliberately-missing
# measured value and parses to NaN — never silently to zero.
function read_case_a_csv(path)
    lines = readlines(path)
    header = strip.(split(first(lines), ','))
    ncols = length(header)
    return map(lines[2:end]) do ln
        cells = split(ln, ','; limit = ncols)
        Dict(header[i] => strip(c) for (i, c) in enumerate(cells))
    end
end
num(s) = (v = tryparse(Float64, s); v === nothing ? NaN : v)
cell(s) = isempty(s) ? "-" : s

The measured agreement (this row, agr_tol = gap_1e-10): BOTH engines certify the full-population point and they AGREE within a measured, stated tolerance. How the row was earned, honestly: at the plain default AGR factory the ADMM loop converged (80 iterations) but the battery-complementarity certificate refused the point on CERTIFICATE NOISE — the complementarity product sat 0.04% over its ~1e-12 relative band at the per-house-divided battery scale. The repo's answer was NEVER a gate change: the bounded, pre-planned solver-precision ladder (default → gap1e-10 → gap1e-12 → gapfeas1e-12, stop-on-first-certified, hard stop) tightened the AGR SOLVER's convergence precision through `solveadmm'sagroptimizerseam — and the FIRST rung (gap1e-10) certified the point at the same 80 iterations. The tolerance is MEASURED from the certified pair: the engines' welfare differs bywelfarereldelta = 6.217147850629488e-8and prices by at mostpricemaxabsdelta = pricemaxreldelta = 0.17819846607479023; the pinned test band is 10× those observed deltas, floored at solver noise (welfare rtol 6.217147850629488e-7, price atol/rtol 1.7819846607479022) and asserted LIVE in the:slow` test item — the former tracked skip is lifted.

Scaling — measured, not assumed

Thesis parameters that are NOT available — and the rule that replaced each

The thesis specifies its Case A population's fine structure in an appendix (its Appendix E) that is not public. Building a population at this size without it required an explicit, deterministic replacement for each unavailable parameter — each stated here, so the construction reads as calibration provenance rather than hidden re-tuning:

Per-house appliance ownershipThe device set is FIXED for every house: one Thermostatic, one Deferrable, one PVBattery — the default population's three-device house shape. No ownership heterogeneity is claimed.
